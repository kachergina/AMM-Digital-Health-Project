# AMM Digital System

A **software simulation** of the Automated Medical Module (AMM) concept from the
school project website.

The AMM Digital System demonstrates how a future AMM could collect, process and
show patient sensor data. It is built as a learning project in Python.

## Important — read this first

- **This is a simulation.** Every temperature, heart rate, SpO2 and respiratory
  rate value is generated by a computer program with random numbers.
- **No real patient data is used.** Nothing here is measured from a human being.
- **This is NOT a real medical device.** It must not be used for medical
  diagnosis, monitoring, or treatment of any kind.
- The processing layer uses simple, transparent rules and **no machine learning**.
  It never produces a medical diagnosis.
- The system exists only to illustrate the AMM concept for a student portfolio.

## Architecture

```
Sensor Simulator  ──▶  Data Processing  ──▶  Flask API  ──▶  Dashboard
(simulator/)           (processing/)          (api/)       (dashboard/)
                                                         app.py serves all
```

- **Sensor Simulator** (`simulator/sensors.py`) generates one SIMULATED reading
  at a time: body temperature, heart rate, SpO2 and respiratory rate, each with
  a UTC timestamp and a `simulated: True` flag.
- **Data Processing** (`processing/analyze.py`) validates the reading, compares
  each vital against clearly named illustrative ranges, and returns a structured
  result with an overall simulated status (`NORMAL`, `ATTENTION` or `REVIEW`).
- **Flask API** (`app.py` + `api/routes.py`) exposes the pipeline over HTTP.

The dashboard and demo pages are planned for a later phase and are not built yet.

## How the simulator works

`generate_reading()` returns a dictionary:

```python
{
    "timestamp": "2026-08-28T08:26:42.836648+00:00",
    "simulated": True,
    "note": "SIMULATED — not real patient data",
    "temperature_c": 36.5,
    "heart_rate_bpm": 60,
    "spo2_percent": 97,
    "respiratory_rate_bpm": 13
}
```

Values use `random` inside plausible human ranges so they change between calls
while remaining clearly a simulation. `SensorSimulator` wraps this in a small
class with `read()` and `read_many(count)`.

## How the processing layer works

`analyze_reading(reading)`:

1. Checks the input is a dictionary with all expected fields.
2. Checks each field is a number (booleans are rejected).
3. Compares each vital to its illustrative range using `analyze_vital()`.
4. Counts how many vitals are out of range and maps that to a status:
   - 0 out of range → `NORMAL`
   - 1 out of range → `ATTENTION`
   - 2 or more     → `REVIEW`
5. If the input is invalid, returns `INVALID` instead of crashing.

The ranges live in named constants (`TEMPERATURE_RANGE`, `HEART_RATE_RANGE`,
`SPO2_RANGE`, `RESPIRATORY_RATE_RANGE`) so the logic stays easy to read. They
are **not** clinically validated medical thresholds.

## API endpoints

| Method | Path           | Description                                            |
|--------|----------------|--------------------------------------------------------|
| GET    | `/api/vitals`  | New simulated reading + its processing result (JSON)  |
| GET    | `/api/status`  | Current simulated AMM system status (JSON)             |

Both responses include `"simulated": True` and the disclaimer text.

```json
    "overall_status": "NORMAL",

      {"name": "temperature_c", "label": "Body temperature", "value": 36.5, "unit": "°C", "low": 36.0, "high": 37.5, "status": "WITHIN"},
```


## How to run the Flask application

Open a terminal inside the `digital_system/` folder and run:

```bash
python3 app.py
```

Then open the dashboard in a browser:

```bash
http://127.0.0.1:5001/
```

The API is also available:

```bash
curl http://127.0.0.1:5001/api/vitals
curl http://127.0.0.1:5001/api/status
```

## Dashboard

The dashboard is a conceptual medical-engineering control interface served by
Flask at `/`. It is **not** a real hospital product and clearly states it is a
simulation.

### What the user can see

- A permanent, highly visible banner:
  **"SIMULATION — SIMULATED DATA — NOT A REAL MEDICAL DEVICE"**, with a short
  note that all values are artificially generated for demonstration.
- The four simulated vitals as clean cards: Body temperature, Heart rate,
  Blood oxygen (SpO₂) and Respiratory rate — each with value, unit, and a
  colour-coded status (WITHIN / BELOW / ABOVE).
- The **simulated system assessment** (NORMAL / ATTENTION / REVIEW) and the
  timestamp of the last reading.
- Two live line charts (heart rate and SpO₂) that update as new readings arrive.
- A **data pipeline** strip (`Sensors → Processing → API → Dashboard`) that
  lights up each stage when a new reading is generated, making the flow visible.
- A list of simulated AMM components shown as "Online (simulation)":
  Thermal camera, LiDAR scanner, Medical sensors, Robotic manipulator,
  UV sterilisation — each with a short description of what it represents in
  the concept (loaded from `GET /api/status`).

### How the simulation works on the page

1. The page loads and immediately calls `GET /api/vitals`.
2. Clicking **Run simulation** requests a fresh simulated reading and updates
   the cards, timestamp, assessment and charts.
3. **Auto refresh** (toggle button) repeats that every 5 seconds. It is off by
   default so the interface stays calm and understandable.
4. The processing status is labelled a *simulated system assessment* — it is a
   simple range check, never a medical diagnosis.

### Files

```
dashboard/
├── templates/index.html     (dashboard page, served at /)
└── static/
    ├── dashboard.css        (separate styling, AMM blue identity)
    └── dashboard.js         (fetches /api/vitals, updates DOM + Chart.js)
```

Charts are drawn with the browser's built-in Canvas API, so the dashboard has
**no external dependencies** and works fully offline (it does not rely on a
CDN). The dashboard styling is intentionally kept separate from the main AMM
website CSS.

### Languages

The dashboard is multilingual (EN / FR / RU) with all user-facing text supplied
by `i18n.py`. The language is selected with a `?lang=en|fr|ru` query parameter
(default English; unknown values fall back to English). The Flask API localizes
its JSON (`/api/vitals`, `/api/status`) using the same parameter, while the
underlying data (`name`, `unit`, status codes) stays language-neutral. The
browser tab uses the existing AMM favicon, served from the project's
`assets/images/` folder.

### Scenario engine, alerts and export

`simulator/sensors.py` can produce presets via `generate_reading(scenario)`:
`normal` (default), `fever`, `low_spo2`, `tachycardia`, `critical`. Unknown
values fall back to `normal`. The dashboard has a localized scenario selector,
a prominent alert banner that changes colour with the overall status
(NORMAL / ATTENTION / REVIEW / INVALID), and **Download JSON / Download CSV**
buttons that export the in-browser session history (last 30 readings).

The same scenario is available on the API with `GET /api/vitals?scenario=...`,
so the abnormal states can be demonstrated on demand.

### Command-line demo

Run a streaming, text-only demo straight from the terminal (no web server
needed):

```bash
python3 -m digital_system.demo                 # from the project root
python3 -m demo --scenario fever --count 4      # from inside digital_system/
```

Options: `--scenario`, `--count`, `--interval`. Every value printed is
simulated and clearly marked as not a real medical device.

## How to run the tests

From the same `digital_system/` folder:

```bash
pytest
```

The suite covers the simulator, the processing layer, both API endpoints, and
the dashboard page (HTTP 200, disclaimer present, static assets load). All
tests confirm the data is simulated and handled safely.
